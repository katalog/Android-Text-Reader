# 왜 이렇게 만들었나 — 설계 이유서

이 문서는 코드가 **무엇을 하는지**가 아니라 **왜 그렇게 생겼는지**를 설명합니다.
기능별 구현은 [FEATURES.md](FEATURES.md), 시나리오별 실행 흐름은 [USER_SCENARIOS.md](USER_SCENARIOS.md),
테스트 계획은 [TESTING.md](TESTING.md)에 따로 있습니다.

각 결정은 **"순진하게 짰다면 → 그게 왜 깨지는지 → 그래서 실제로는 → 대신 치른 대가"** 순서로 씁니다.
순진한 쪽을 먼저 보면 실제 코드가 왜 그 모양일 수밖에 없는지가 자연히 보입니다.

---

## 먼저 — 이 앱이 실제로 푸는 어려운 문제는 셋뿐

1. **페이지는 고정된 게 아니다.** 글자 크기를 한 단계만 키워도 책 전체의 페이지 나누기가 완전히
   달라진다. "3페이지"라는 말이 어제와 오늘 다른 내용을 가리킨다.
2. **소설 한 권이 수백만 자다.** 무심코 "전부 처리"하는 코드를 쓰면 그 순간 앱이 몇 초씩 멈춘다.
3. **안드로이드는 이제 파일 경로로 파일을 못 읽는다.** `/sdcard/책.txt` 같은 접근은 막혔다(스코프드
   스토리지). 사용자가 직접 고른 폴더에 대한 권한을 받아 그것만 읽어야 한다.

아래 결정들은 거의 전부 이 셋 중 하나에서 나온다.

## 1. 읽던 위치를 페이지가 아니라 글자 번호로 저장하는 이유

> 문제 ①에서 나온 결정 — 이 앱에서 가장 중요한 한 가지

**✗ 순진하게 짰다면**
책을 덮을 때 "37페이지를 보고 있었다"를 저장하고, 다음에 열 때 37페이지를 보여준다.

**그런데 이게 왜 깨지나**
글자 크기를 키우면 한 페이지에 들어가는 글자가 줄어든다. 어제의 37페이지는 오늘 25페이지쯤의 내용이
된다. 화면을 가로로 돌려도, 여백을 바꿔도, 폰트를 바꿔도 마찬가지다. 저장해둔 숫자는 그대로인데 그
숫자가 가리키는 내용이 바뀌어 버린다.

**✓ 그래서 실제로는**
"책 전체에서 **23,481번째 글자**를 보고 있었다"를 저장한다. 글자 번호는 폰트를 바꾸든 화면을 돌리든
절대 변하지 않는다. 페이지는 저장하는 값이 아니라, 그 글자 번호로부터 **매번 다시 계산되는 파생값**이
된다.

**대신 치른 대가**
"전체 320페이지 중 37페이지" 같은 표시를 못 한다. 전체 페이지 수를 알려면 책 전체를 다 나눠봐야
하는데, 그건 문제 ② 때문에 안 하기로 했으니까. 그래서 앱은 페이지 번호 대신 **퍼센트**를 보여준다.

> **코드에서 확인:** `data/db/BookEntity.kt`에는 `lastReadCharOffset`(글자 번호)과
> `lastReadProgressPercent`만 있고 페이지 번호 필드가 아예 없다. 이 앱에서 영구 저장되는 위치 정보는
> 그 둘이 전부다.

## 2. 책을 열 때 페이지를 전부 나누지 않는 이유

> 문제 ②에서 나온 결정

**✗ 순진하게 짰다면**
책을 열 때 처음부터 끝까지 훑으면서 페이지 경계를 전부 계산해 리스트로 만들어 둔다. 그러면 "다음
페이지"는 리스트에서 다음 항목을 꺼내면 되니 간단하다.

**그런데 이게 왜 깨지나**
글자 폭을 재는 건 공짜가 아니다. 1,000페이지짜리 소설이면 열 때마다 1,000번 측정해야 하고 그동안
화면이 멈춘다. 게다가 사용자가 글자 크기를 한 단계 키우면 그 1,000번을 **처음부터 다시** 해야 한다.
설정을 만지작거릴 때마다 앱이 얼어붙는다.

**✓ 그래서 실제로는**
지금 화면에 보여줄 **한 장만** 계산한다. "다음"을 누르면 현재 페이지가 끝난 글자 번호부터 딱 한 장을
새로 잰다. "이전"은 앞으로 넘어오면서 쌓아둔 **방문 이력 스택**에서 꺼내 쓰니 다시 계산할 필요조차
없다.

**대신 치른 대가**
검색 결과로 책 한가운데로 점프한 직후처럼 **이력이 비어 있을 때**는 "이전 페이지"를 알 방법이 없다.
이때만 예외적으로 조금 앞에서부터 되짚어 계산해 추정한다(`Paginator.onePageEndingAt`). 조금 어긋나도
상관없다 — 한 번 앞으로 넘기는 순간 이력이 정확한 값으로 채워진다.

## 3. 페이지 높이를 문단별로 더하지 않고 통째로 재는 이유

> 실제로 겪은 버그가 만든 결정

**✗ 순진하게 짰다면**
문단을 하나씩 높이를 재서 더해 나가다가, 화면 높이를 넘기 직전 문단까지를 한 페이지로 삼는다.

**그런데 이게 왜 깨지나**
실제 화면은 페이지 전체를 **텍스트 한 덩어리**로 그린다. 그런데 문단을 따로따로 잰 높이의 합은 그것들을
한 번에 그렸을 때의 높이와 정확히 같지 않다(줄 간격이 붙는 방식이 다르다). 그래서 "들어간다"고
판단했는데 실제로는 넘쳐서 **마지막 줄이 화면 밖으로 잘려 안 보이는** 버그가 났다.

**✓ 그래서 실제로는**
후보 구간 전체를 **한 번의 `TextMeasurer.measure` 호출**로 잰다. 재는 방식과 그리는 방식을 똑같이 맞춘
것이다. 넘치면 그때 레이아웃에 "몇 줄까지 들어가는지"를 물어서 거기서 페이지를 끊는다.

> **이게 왜 중요한가:** 설계 취향 문제가 아니라 실제 버그를 고친 흔적이다. `data/parser/Paginator.kt`
> 맨 위 주석에 그 경위가 남아 있다. **코드에 이유가 적혀 있으면 대개 누군가 그걸로 한 번 당한 것이다.**

## 4. 목차를 데이터베이스에 저장하지 않는 이유

**✗ 순진하게 짰다면**
책을 처음 열 때 챕터 제목을 찾아 DB에 저장해두고, 다음부터는 그걸 읽어 쓴다.

**그런데 이게 왜 깨지나**
챕터를 찾는 규칙(정규식)은 계속 손보게 된다. 규칙을 고치는 순간 이미 저장된 목차는 **옛날 규칙으로 만든
결과**가 되어 실제와 어긋난다. 그걸 맞추려면 저장된 걸 전부 지우고 다시 만드는 처리와 DB 스키마
마이그레이션까지 딸려온다. 규칙 하나 고치는 비용이 갑자기 커진다.

**✓ 그래서 실제로는**
저장하지 않고 **책을 열 때마다 그 자리에서 다시 찾는다.** 규칙을 얼마든지 고쳐도 마이그레이션이 필요
없고, 하나도 못 찾으면 그냥 "목차 없음"으로 자연스럽게 처리된다.

**대신 치른 대가**
책을 열 때마다 전체 텍스트를 줄 단위로 스캔한다. 그래서 이 작업은 **첫 화면 표시를 기다리게 하지 않고**
백그라운드로 돌리고, 끝나는 대로 목차만 나중에 채운다(`ReaderViewModel.redetectChapters`). 사용자는 첫
페이지를 즉시 보고, 목차 버튼은 잠깐 뒤에 채워진다.

## 5. 자동 넘김을 `boolean` 두 개가 아니라 상태 하나로 만든 이유

**✗ 순진하게 짰다면**
`타이머켜짐: Boolean`, `TTS켜짐: Boolean` — 기능이 둘이니 스위치도 둘.

**그런데 이게 왜 깨지나**
둘 다 `true`인 상태를 **타입이 허용해 버린다.** 그러면 타이머도 페이지를 넘기고 TTS도 페이지를 넘겨서
두 칸씩 건너뛰는 상황이 생긴다. 이걸 막으려면 "한쪽을 켤 때 다른 쪽을 끄는" 코드를 켜는 지점마다
빠짐없이 넣어야 하는데, 한 군데만 빠뜨려도 버그다.

**✓ 그래서 실제로는**
값이 셋 중 하나뿐인 상태 하나로 만들었다 — `AutoAdvanceMode.OFF / TIMER / TTS`. 동시에 켜진 상태는
**애초에 표현할 수가 없다.** 잊어버릴 코드 자체가 존재하지 않으니 그런 버그가 원천적으로 불가능하다.

> **다른 곳에도 그대로 쓰이는 원칙:** "잘못된 상태를 만들지 않도록 조심한다"가 아니라 **잘못된 상태를
> 애초에 표현할 수 없게 타입을 만든다.** 버그를 안 내려고 노력하는 대신, 그 버그를 낼 방법 자체를
> 없애는 쪽이 항상 더 싸다.

## 6. 라이브러리를 이것들로 고른 이유

각각 "이게 없으면 대신 뭘 직접 해야 하는가"로 보면 선택 이유가 분명해진다.

| 선택 | 이게 없으면 직접 해야 하는 일 | 고른 이유 |
|---|---|---|
| **SAF** | 안드로이드 10부터 임의 파일 경로 접근이 막혀서, 애초에 파일을 열 방법이 없음 | 선택의 여지가 없는 항목. 사용자가 고른 폴더에 대해 **앱을 껐다 켜도 유지되는 권한**을 받는 유일한 길 |
| **Room** | SQL 문자열을 손으로 쓰고, 오타는 실행해봐야 알고, 커서를 직접 돌리고, 스레드 관리까지 | SQL을 **컴파일할 때 검사**해주고, 데이터가 바뀌면 화면이 자동 갱신되는 Flow를 그대로 줌 |
| **DataStore** | SharedPreferences는 메인 스레드를 막는 문제와 비동기 안전성을 직접 신경 써야 함 | 구글이 만든 SharedPreferences 후계. 설정 변경이 **Flow로 흘러나와** 화면이 알아서 따라감 |
| **juniversalchardet** | 한글 txt는 UTF-8·EUC-KR·CP949가 뒤섞여 있음. 잘못 읽으면 전부 깨진 글자. 인코딩 추측을 직접 구현해야 함 | 이 앱이 다루는 파일 특성상 **없으면 안 되는** 기능 |
| **Compose** | XML 레이아웃 + 뷰를 손으로 찾아 값 넣기. 상태와 화면이 어긋나는 버그를 계속 잡아야 함 | "상태가 이러면 화면은 이렇다"만 쓰면 되는 선언형 UI. 설정 값이 화면에 바로 반영돼야 하는 이 앱 구조와 잘 맞음 |
| **Go** (PC 서버) | PC에 파이썬이나 런타임을 따로 깔게 해야 함 → 사용자가 포기함 | 표준 라이브러리만으로 HTTPS 서버와 자체 서명 인증서 생성까지 다 됨. 결과물이 **설치 필요 없는 exe 하나**. 리눅스 CI에서 윈도우용 크로스컴파일도 됨 |

### 그리고 일부러 안 쓴 것들

| 안 쓴 것 | 보통은 쓰는데 | 여기서 안 쓴 이유 |
|---|---|---|
| **Hilt / Koin** (DI 프레임워크) | 객체를 알아서 만들어 넣어주는 도구 | 화면이 두 개뿐인 앱. 필요한 걸 생성자로 받고 Factory에서 손으로 조립하는 걸로 충분하다. **그 생성자 주입만으로 테스트에 가짜 구현을 끼워 넣는 목적은 이미 달성**돼서(`FakeFolderBrowser`), 프레임워크를 얹을 이유가 없었다 |
| **Retrofit / OkHttp** (앱 쪽 네트워크) | 서버 API를 부를 때 거의 항상 씀 | 이 앱이 부르는 요청은 전부 합쳐 서너 개뿐. 자바 표준 `HttpURLConnection`으로 충분하고 의존성이 줄어든다. (다만 **테스트**에서는 가짜 서버용으로 MockWebServer를 쓴다 — 앱에는 안 들어감) |
| **클라우드 저장소** (동기화용) | 기기 간 파일 동기화 하면 보통 이걸 씀 | 수 MB~십수 MB짜리 파일이 백수십 개라 용량이 부담이고, 백그라운드 자동 동기화가 **배터리를 계속 먹는다.** 그래서 "내가 누를 때만, 내 PC에서 직접" 가져오는 방식을 골랐다 |

## 7. 동기화 쪽의 "왜"들

**왜 인증서를 CA로 검증하지 않고 "지문"을 기억하나?**
공인 인증서는 `example.com` 같은 도메인에만 발급된다. 집 안 PC의 `192.168.0.42`에는 아무도 인증서를 안
준다. 그래서 PC가 스스로 만든 인증서를 쓰되, **SSH에 처음 접속할 때와 똑같은 방식**으로 — 최초 한 번 그
지문을 기억해두고 다음부터는 같은 지문인지만 확인한다(TOFU).

**왜 파일 비교에 수정시각을 안 쓰고 크기만 보나?**
안드로이드가 SAF로 파일을 만들 때 **수정시각을 PC 원본 값으로 지정할 수가 없다.** 받은 시각이 그대로
박힌다. 그래서 수정시각을 비교에 넣으면 내용이 그대로여도 항상 달라 보여서, 동기화할 때마다 안 바뀐
파일까지 전부 다시 받았다. 실제로 겪은 버그였고 크기 비교만 남겨 고쳤다(`computeSyncDelta`).

**왜 "연결 테스트"가 조회가 아니라 쓰기인가?**
시크릿이 틀려서 서버가 막았을 때 **조회는 에러가 아니라 그냥 빈 결과**가 온다. "데이터가 없어서 비었는지,
권한이 없어서 비었는지" 구분이 안 된다. 반면 쓰기는 권한이 없으면 명확하게 거부 응답이 온다. 그래서 더미
값으로 쓰기를 시도한다.

**왜 500자나 차이 나야 "다른 기기가 더 읽었다"고 알리나?**
PC(VSCode)는 **커서가 있는 글자 위치**를, 안드로이드는 **페이지가 시작하는 글자 위치**를 보낸다. 같은
문단을 보고 있어도 기준이 달라 수백 자쯤 어긋난다. 이 차이를 무시하지 않으면 실제로는 같은 곳인데도
팝업이 계속 떴다 — 처음엔 그렇게 만들었다가 고친 부분이다.

## 8. 이제 이 순서로 5개만 읽어보면 된다

전체를 훑지 말고 이것만. 위 이야기가 코드에서 그대로 보이는 지점들이다.

1. **`data/datastore/ReaderSettings.kt`** — 앱이 기억하는 모든 설정이 한 화면에 들어 있다. 여기부터
   시작하면 나머지 코드가 전부 "이 값들을 읽어서 화면에 반영하는 구조"로 보이기 시작한다. 5분.
2. **`data/db/BookEntity.kt`** — 영구 저장되는 건 이것뿐. **페이지 번호 필드가 없다는 것**을 눈으로
   확인할 것. §1 결정이 코드로 나타난 결과다.
