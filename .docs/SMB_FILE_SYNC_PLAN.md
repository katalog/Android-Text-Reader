# 계획: SMB 기반 PC → 안드로이드 단방향 파일 동기화

**상태**: 계획 단계, 구현 시작 전.

## 배경

지금은 Syncthing-Fork가 PC와 폰 사이에 소설 `.txt` 폴더를 계속 실시간으로 미러링해주고 있고, 그 위에
[VSCODE_SYNC_PLAN.md](VSCODE_SYNC_PLAN.md)의 읽기 위치 동기화가 얹혀 있다. Syncthing 자체(페어링,
디바이스 ID, 폴더 ID 매칭, 디스커버리/릴레이 서버)가 설정이 복잡하다고 느껴져서, 이 부분을 더 단순한
것으로 교체하고 싶다는 요청에서 시작.

## 검토했던 대안과 왜 이 방향인지

- **클라우드 드라이브(OneDrive/Google Drive)로 교체**: 앱 코드 변경이 전혀 없는 게 장점이지만,
  "오프라인 사용 가능" 폴더는 백그라운드에서 주기적으로 변경사항을 폴링하는 서비스가 계속 돌아서
  배터리를 계속 소모한다 — 이 앱의 "완전 오프라인, 백그라운드 없음" 철학과 안 맞음.
- **자체 버튼 + Supabase Storage 릴레이**: 이미 검증된 인프라를 재사용할 수 있는 장점은 있지만, 외부
  클라우드 계정의 저장 용량(무료 티어 1GB)에 계속 기대는 구조라 라이브러리가 커지면 언젠가 한계에
  부딪힐 수 있음.
- **채택: SMB(Windows 기본 파일 공유)를 전송 수단으로, 실제 복사는 앱의 "동기화" 버튼이 트리거** — 세
  우려를 동시에 해결함:
  - 클라우드 계정/저장 용량 제한 없음 (LAN 안에서만 오감, PC 저장공간이 곧 한계)
  - 평소엔 아무 백그라운드 서비스도 안 돎(버튼 누를 때만 접속) → 배터리 영향 없음
  - PC 쪽 설치가 필요 없음(Windows 폴더 공유는 OS 기본 기능, 폴더 우클릭 → 속성 → 공유)
  - 복사가 끝나면 로컬 파일이 되므로 PC가 꺼져 있어도 그 다음부턴 오프라인으로 읽기 가능 (지금 철학
    유지 — Syncthing과 최종 결과물은 동일)

## 목표 (이번 범위)

**단방향, PC → 폰만.** 사용자 확인: 파일 추가/삭제는 PC에서만 일어나고 폰에서는 안 함. 그래서:
- 폰 → PC로 올리는 경로는 없음 (VSCode 확장 쪽 코드 변경 전혀 불필요 — PC는 그냥 수동적인 SMB
  공유일 뿐, 별도 프로그램 설치 없음)
- 델타 계산은 "원격에 있는데 로컬에 없다/다르다 → 받는다", "로컬에 있는데 원격에 없다 → 지운다"
  두 방향만 있으면 됨. 충돌(양쪽에서 동시 수정) 개념 자체가 없음 — 로컬은 항상 원격의 거울.

## 핵심 설계 결정

### 1. 동기화 대상 폴더 = 기존 라이브러리 SAF 루트 그대로

새로운 "동기화 전용 폴더" 개념을 따로 만들지 않는다. 사용자가 이미 폴더 선택 화면에서 고른 SAF
트리(지금 Syncthing이 채워주고 있는 바로 그 폴더)를 그대로 동기화 대상으로 쓴다. 장점:
- `BookEntity`/`relativePath`/챕터 인식 등 기존 파이프라인이 전혀 안 바뀜 — SMB로 받아온 파일이든
  수동으로 넣은 파일이든 앱 입장에선 "SAF 트리 안의 `.txt` 파일"로 동일하게 보임.
- VSCode 쪽 읽기 위치 동기화(§상대 경로)도 그대로 작동 — 같은 트리, 같은 상대 경로 규칙.

### 2. SMB 클라이언트 — `smbj` (+ `minSdk` 24 → 26 상향)

처음엔 `jcifs-ng`(minSdk 24 그대로 유지 가능)로 계획했다가, **동기화 대상 파일이 개당 수 MB~십수
MB씩 여러 개**라는 걸 확인하고 재검토함 — jcifs-ng 관리자 본인이 "약 30MB/s로 처리량이 제한돼 있고
이를 넘으려면 라이브러리를 거의 새로 짜야 한다"고 밝힌 상태라, 파일 크기가 작을 땐 무관했지만 이
규모(전체 동기화 시 수백MB~1GB대)에서는 체감되는 차이(수십 초 vs 십수 초)를 만든다. 실제로 오픈소스
비디오 플레이어 프로젝트(`nova-video-player/aos-AVP`)도 같은 이유로 jcifs-ng → smbj 전환 이슈를 열어둔
전례가 있음. `smbj`가 SMB2/3 처리량에서 더 빠르다는 점을 확인하고 `smbj`로 전환 — 대신 `smbj`는
Android 8.0(API 26)부터만 지원해서, 이 앱의 `minSdk`를 24 → 26으로 올려야 함(`app/build.gradle.kts`,
`CLAUDE.md`도 같이 갱신 — Phase 1 작업 항목에 포함). 안드로이드 7은 출시 10년째라 실질적 지원 범위
축소는 미미할 것으로 판단.
OkHttp 같은 무거운 의존성 추가를 피해온 지금까지 기조와는 다르게, SMB 프로토콜 자체는 직접
구현하기엔 비용이 너무 크므로 이번만 예외로 라이브러리를 새로 들인다 (`gradle/libs.versions.toml`에
등록).

### 3. 델타 계산 — 상대 경로 + 크기/수정시각 비교

- 원격: `smbj`로 공유 루트부터 재귀적으로 `.txt`/`.zip` 파일 나열 (경로/크기/수정시각) — zip은
  내용을 열지 않고 파일 자체를 통째로 비교/복사 대상으로만 취급(§열린 질문 4).
- 로컬: 기존 SAF 트리를 재귀적으로 나열 (`DocumentFile.listFiles()`, 이미 `SafFolderBrowser`가 쓰는
  API 그대로 재사용 가능).
- 상대 경로 정규화는 `RelativePath.kt`의 기존 함수를 그대로 재사용(구분자 통일/NFC/소문자화) —
  VSCode 동기화 때 이미 검증된 로직.
- 비교 결과 세 묶음: **새로 받을 파일**(원격에만 있음), **다시 받을 파일**(양쪽에 있지만 크기 또는
  수정시각이 다름), **지울 파일**(로컬에만 있음, 원격에서 삭제된 것으로 간주).

### 4. 로컬 쓰기 — SAF `DocumentFile` API

`DocumentFile.createFile()` / `ContentResolver.openOutputStream()`으로 신규/갱신 파일 쓰기,
`DocumentFile.delete()`로 삭제. 원격에 하위 폴더가 있으면 로컬에도 대응하는 `DocumentFile` 폴더를
먼저 만들고 그 안에 씀 — Syncthing이 지금 하는 것과 같은 폴더 구조 유지.

### 5. 연결 설정 — 기존 "공유 시크릿" UX 패턴 + 자동 탐색

인증 없는 "Everyone" 공유로 확정했으므로(§열린 질문 1) 자격증명 입력/저장은 필요 없다. `ReaderSettings`에
SMB 필드 추가(호스트, 공유 이름, 공유 안의 하위 경로) + 설정 화면에 입력 필드들과 "연결 테스트" 버튼 —
Supabase 공유 시크릿 설정 때 이미 검증된 패턴(입력 → 테스트 → 성공 시에만 동작) 그대로 따른다.

- **호스트 찾기 (참고 프로젝트 조사 후 결정)**: 처음엔 Windows 컴퓨터 이름을 입력받아 `jcifs-ng`의
  NetBIOS 이름 해석에 맡기는 안을 생각했는데, 실제 오픈소스 SMB 스캐너 앱
  ([The3211/NetworkExplorer-Android](https://github.com/The3211/NetworkExplorer-Android))의 README를
  보면 NetBIOS 이름 해석은 자기들도 TODO로 미뤄둔 신뢰도 낮은 방식이었다. 대신 그 프로젝트가 실제
  쓰는 방식은 **로컬 서브넷 445 포트 스캔**(폰의 현재 IP에서 `/24` 서브넷을 유추 → 254개 호스트를
  병렬로 짧은 타임아웃(~1초)으로 445 포트 접속 시도 → 응답하는 호스트만 후보로 표시)이었다. 이 방식을
  채택 — 설정 화면에 "PC 찾기" 버튼을 두고 스캔 결과를 목록으로 보여주면 탭 한 번으로 호스트 필드가
  채워진다.
  - **수동 입력은 항상 병행 지원**한다 — 스캔이 실패하거나(방화벽, 다른 서브넷 등) 원치 않을 때를
    대비해 호스트/IP 직접 입력 필드도 그대로 둔다. 미니멀한 오픈소스 SMB 클라이언트
    ([egdels/SambaLite](https://github.com/egdels/SambaLite))도 자동 탐색 없이 이 방식만으로 동작함 —
    검증된 최소 구현 패턴.
  - 포트 스캔 자체는 순수 TCP 소켓 접속이라 SMB 라이브러리 선택(§2)과 무관 — smbj로 바꿔도 이 방식
    그대로 유지.
- **공유 이름**: 게스트 접근이 허용된 서버는 `smbj`로 공유 목록 자체를 나열해볼 수 있는지 Phase 1
  구현 중 실제 Windows로 확인 — 되면 자동 나열, 안 되면 공유 이름도 수동 입력.

### 6. 삭제된 파일의 `BookEntity` 처리

PC에서 파일이 지워져서 로컬에서도 지워지면, 그 파일을 가리키던 `BookEntity`(읽던 위치 기록)가
고아 상태가 된다. 최소 범위로는 "이어서 읽기" 목록에서 파일이 실제로 존재하는지 확인해서 없으면
걸러내는 정도만 하고, `BookEntity` 행 자체를 지우는 건 다음 단계로 미뤄도 됨(읽기 기록이 남아있어도
기능 고장은 안 남 — 그냥 안 보이는 유령 행).

## 페이즈별 구현 계획 + 예상 규모

| 페이즈 | 내용 | 규모 |
|---|---|---|
| **0. PC 준비** | Windows 폴더 공유 켜기, 공유 이름 확인, 인증 방식 결정(§5 열린 질문) — 코드 아님 | 사용자 작업, 5분 |
| **1. SMB 클라이언트 기반** | `minSdk` 24→26 상향(`build.gradle.kts`, `CLAUDE.md`), `smbj` 의존성 추가, `data/sync/SmbSyncClient.kt`(연결 테스트 + 원격 파일 재귀 나열), 로컬 서브넷 445 포트 스캐너(§열린 질문 2), `ReaderSettings`에 필드 추가 + 설정 화면 UI(입력 필드들 + "PC 찾기" 스캔 버튼 + 연결 테스트 버튼) | 중 — Supabase 클라이언트+설정 UX 만들 때보다 스캐너만큼 조금 더 큼 |
| **2. 델타 계산 + 로컬 쓰기** | 로컬 SAF 트리 재귀 나열, 원격/로컬 비교해서 신규·갱신·삭제 목록 산출, `DocumentFile`로 실제 쓰기/삭제(하위 폴더 생성 포함) | 대 — 이번 기능에서 가장 새로운 부분, SAF 쓰기 API가 처음 다루는 영역 |
| **3. UI 연동** | `LibraryViewModel`에 동기화 트리거 + 진행 상태(몇 개 중 몇 개, 에러), `LibraryScreen`에 "동기화" 버튼 + 진행 표시 + 완료/에러 스낵바, 삭제 파일의 `BookEntity` 정리(§6) | 소~중 |
| **4. 실기기 검증** | 신규/수정/삭제 각 시나리오, 대용량 라이브러리 동기화 시간, 네트워크 끊김·인증 실패 등 실패 케이스, PC 꺼진 상태에서 이미 받은 파일 오프라인 열람 확인 | 필수, 반복 소요 예상(지금까지 다른 기능들도 실기기 검증에서 버그가 꽤 나왔음) |

**전체 규모 가늠**: VSCode 읽기-위치 동기화 프로젝트의 "스테이지 2(안드로이드)" 하나 분량과 비슷하거나
약간 더 큼(SAF 쓰기가 이번에 새로 다루는 영역이라). 다만 VSCode 확장 쪽 작업(스테이지 3에 해당하는 것)이
이번엔 통째로 없음 — PC는 그냥 수동적인 공유 폴더일 뿐이라 PC 쪽 코드가 전혀 없기 때문. 그래서
총량으로 보면 지난 기능 전체(3 스테이지)보다는 뚜렷하게 작다.

## 열린 질문 — 결론

1. **SMB 인증 방식**: 비밀번호 없는 "Everyone" 읽기 전용 공유로 확정.
2. **PC 찾기(호스트 지정 방식)**: NetBIOS 이름 자동 해석 대신 **로컬 서브넷 445 포트 스캔** 방식으로
   확정 — 참고한 오픈소스 SMB 스캐너(NetworkExplorer-Android)도 실제로 이 방식을 쓰고 있고, 자기들도
   NetBIOS 이름 해석은 TODO로 미뤄둔 신뢰도 낮은 방식이었다(§5 참고). "PC 찾기" 버튼으로 스캔 → 응답한
   호스트 목록에서 탭 한 번으로 선택, 실패 시엔 호스트/IP 직접 입력으로 폴백(SambaLite와 동일 패턴).
3. **하위 폴더 지원 범위**: 재귀적으로 전체 폴더 구조 미러링 — Syncthing과 동일하게 동작.
4. **zip 파일**: 동기화 대상에 `.zip`도 포함 — 내용을 열어보지 않고 파일 자체를 통째로 복사만 하면
   기존 `BookSource.ZipEntryTxt` 로직이 그대로 읽어줌. `.txt`/`.zip` 둘 다 델타 비교 대상 확장자.

## 브랜치 전략 / 배포

이 기능은 별도 브랜치에서 작업하고, `main`에 머지하기 전에도 그 브랜치 커밋을 가리키는 태그를 푸시해서
릴리스를 만들어볼 수 있다 — `release.yml`은 `push: tags: v*`에만 반응하고 브랜치 조건이 없어서,
브랜치가 무엇이든 태그가 가리키는 커밋 기준으로 그대로 빌드/배포된다. 다만 이렇게 만든 릴리스가
GitHub에서 기본적으로 "Latest"로 표시돼 일반 사용자(Obtainium 등 자동 업데이트 도구 포함)에게 베타가
노출될 수 있으니, 브랜치 상태에서 만든 릴리스는 만든 직후 `gh release edit <태그> --prerelease`로
프리릴리스 표시해둔다.
